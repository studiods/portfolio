문제는 오래된 도구 하나가 아니라 기록·책임·목표가 연결되지 않는 업무 구조였습니다.

01.1 / OBSERVATION

익숙하다는 이유로,
불편하고 휘발되는 방식이 계속 사용되고 있었습니다.

도구가 낡았다는 사실보다 그 방식 때문에 프로젝트 맥락이 남지 않는 것이 더 큰 문제였습니다.

01 / MEMO7 DAYS

일주일 뒤 사라지는 쪽지

작성 중 끊기면 내용이 날아가기도 했고, 요청·수정·승인 이력이 일주일 뒤 함께 사라졌습니다.

02 / WBSSTATIC

계획은 있지만 상태는 보이지 않았습니다.

WBS는 있었지만 누가 무엇을 얼마나 진행했는지 실시간으로 추적하기 어려웠습니다.

03 / STORYBOARDPPT

PO의 SB도 폐쇄형 파일로 흘렀습니다.

Storyboard를 PowerPoint로 작성하고 수정본과 배포도 쪽지로 전달해 최신 버전과 변경 이유가 흩어졌습니다.

회의실 일정도 종이로 조율했습니다.

회의실 밖에 종이를 붙여 예약했고, 일정 변경과 중복 확인도 사람이 직접 맞춰야 했습니다.

툴을 정해 놓고 설득하지 않고, 팀별 인터뷰와 업무 관찰을 통해 필요한 구조부터 찾았습니다.

SYNTHESIS

핵심 문제는 쪽지가 아니라, 기록이 휘발되고 상태가 보이지 않으며 역할과 목표가 연결되지 않는 구조였습니다.

가장 심각한 점은 모두가 비효율을 알고 있어도 익숙한 방식에 맞춰 수동적으로 진행하고 있었다는 것입니다. 그래서 새 메신저 도입이 아니라, 먼저 일의 정의와 책임·결정·기록이 남는 방식을 다시 설계하기로 했습니다.

01.3 / AS-IS

기존 방식은 요청을 전달하는 데는 익숙했지만,
프로젝트를 함께 운영하는 구조는 아니었습니다.

AS-IS / PASSIVE HAND-OFF

요청 → 파일 → 쪽지 → 확인 → 재확인

  • 목표보다 화면과 일정이 먼저 고정됩니다.
  • 담당자별 1:1 소통으로 정보가 분산됩니다.
  • 진척도와 Owner를 매번 다시 확인합니다.
  • 수정 이유와 결정이 다음 단계에 남지 않습니다.
→
NEEDED / SHARED OPERATING MODEL

목표 → 역할 → 실행 → 상태 → 결정 기록

  • 문제와 목표를 먼저 공동으로 맞춥니다.
  • 하나의 프로젝트 공간에서 상태를 공유합니다.
  • Owner·일정·자료·이슈를 실행 단위에 연결합니다.
  • 변경과 판단을 다시 찾을 수 있게 남깁니다.
02

툴을 고르기 전에,

PO·UX·개발·사업이 화면을 넘겨받는 관계가 아니라 문제를 함께 해결하는 구조를 목표로 했습니다.

02.1 / R&R

누가 화면을 그리느냐보다,
어떤 판단을 책임지는지를 먼저 정의했습니다.

세부 설계 전에 PRD 기반 Sync와 Kick-off를 두고 목표·Scope·제약을 함께 검증하도록 했습니다.

01 / PO

문제·목표·정책과 우선순위

비즈니스 목표, 해결할 문제, 정책, PRD, 로드맵과 전체 일정·우선순위를 책임집니다.

02 / UX

사용자 흐름과 경험의 구체화

UX 방향, 정보 구조, Wireframe, Prototype, UI Design과 상세 경험의 완성도를 책임집니다.

03 / DEV

기술 가능성과 더 나은 대안

후반 구현자가 아니라 초반부터 참여해 기술 제약과 최신 스펙 적용 시 가능한 대안을 함께 결정합니다.

04 / BUSINESS

운영 조건과 사업 우선순위

현장·운영·매출·정책 조건을 공유하고 목표와 실제 운영 사이의 간극을 함께 조정합니다.

02.2 / DECISION FLOW

업무의 흐름도 전달 중심에서,
공동 판단이 남는 흐름으로 바꿨습니다.

01 / DEFINE

문제·목표 정의

02 / SYNC

사전 Sync

03 / DESIGN

UX 구체화

Flow·Wireframe·Prototype으로 경험을 설계합니다.

04 / FEASIBILITY

기술 검증

개발이 구현 가능성과 더 나은 기술 대안을 함께 검토합니다.

05 / DECIDE

결정 기록

06 / TRACK

상태 추적

Owner·일정·상태·자료·이슈를 한 실행 단위에서 관리합니다.

02

목표와 Scope를 설계 전에 맞춥니다.

PRD·Kick-off를 통해 무엇을 왜 하는지 먼저 합의합니다.

03

진행 상황을 묻지 않아도 보이게 합니다.

04

자료와 논의를 한 공간에 둡니다.

05

회의는 안건이 있을 때 시작합니다.

Agenda와 필요한 문서를 사전에 공유하고 회의 후 결정을 남깁니다.

06

도구는 최소화하고 연결합니다.

Teams·Planner·Lists·Calendar를 중심으로 채널 수를 줄이고 다음 단계에서 Jira·자동화를 연결합니다.

팀별 인터뷰

부서별 배포

03.2 / SYSTEM

쪽지를 없애는 것이 목표가 아니라,
업무가 남고 연결되는 환경을 만들었습니다.

TEAMS / CHANNEL

공식 소통 공간을 만들었습니다.

타 부서 요청은 Webex·Teams로 유도하고, 공식 논의는 Channel·Thread에서 이어지도록 전환했습니다.

PLANNER / TICKET

프로젝트 상태가 보이게 했습니다.

업무를 Ticket 단위로 등록하고 Owner·일정·상태·자료·문제점을 한 공간에서 공유했습니다.

LISTS / REQUEST

반복 요청은 구조화했습니다.

정형 요청과 데이터 취합 등 반복 업무는 Lists 기반으로 형식을 맞춰 누락과 재확인을 줄였습니다.

CALENDAR / SCHEDULE

일정을 투명하게 공유했습니다.

공용 일정과 휴가·외근·집중 업무를 Calendar에 연결해 일정 확인과 조율을 한 곳에서 진행하도록 했습니다.

ROOM / RESERVATION

종이 예약을 온라인으로 바꿨습니다.

회의실 예약 프로세스와 페이지를 제작해 배포했고, 종이를 붙여 조율하던 방식을 온라인 예약으로 전환했습니다.

NEXT / AUTOMATION

다음은 채널 축소와 자동화입니다.

Jira 도입, 채널 통합, Power Automate 연계를 통해 상태 확인과 반복 알림을 더 줄이는 방향으로 확장하고 있습니다.

공식 업무는 개인 쪽지가 아닌 Channel에 남깁니다.

진행률보다 상태와 Blocker를 공유합니다.

06

업무 종료 후에도 결정과 자료가 남아야 합니다.

01 / TIME

상태 확인·자료 탐색 시간

업무 현황을 묻고 최신 자료를 찾는 데 걸리는 시간을 Before/After로 측정합니다.

02 / REWORK

변경·재작업 횟수

목표·Scope·정책의 불일치로 발생하는 재작업과 수정 왕복 횟수를 추적합니다.

03 / LEAD TIME

요청부터 완료까지의 Lead Time

Ticket 생성부터 완료까지 걸리는 시간과 Blocker 체류 시간을 측정합니다.

04 / TRACE

결정 기록률

중요 변경이 이유·Owner·결정과 함께 남는 비율을 확인합니다.

05 / ADOPTION

공식 Channel·Ticket 정착률

쪽지·개별 요청이 아닌 공식 업무 공간에서 처리되는 비율을 추적합니다.

06 / SCALE

Jira·Automation으로 확장

프로세스가 안정되면 Jira와 Power Automate를 연결해 반복 운영까지 줄입니다.

LEADERSHIP

제가 바꾸려 했던 것은 메신저가 아니었습니다. 문제를 함께 정의하고, 진행 상황을 서로 묻지 않아도 보이며, 결정과 학습이 다음 업무까지 남는 조직의 운영 방식을 만드는 일이었습니다.
