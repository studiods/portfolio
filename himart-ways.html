LOTTE HIMART / WAYS OF WORKING / 2024—NOW

휘발되는 소통을 줄이고,
일이 남는 방식을 만들었습니다.

오래된 쪽지·메신저·PPT 중심의 협업에서는 요청과 변경 이유가 쉽게 사라지고, UX가 화면이 이미 정해진 뒤 참여하는 경우도 많았습니다. 사람을 바꾸기보다 문제·역할·결정·일정이 남는 흐름을 만들고, UX가 더 앞에서 문제를 함께 정의할 수 있는 구조를 설계했습니다.

01

문제는 도구보다,
결정이 어디에 남는지 알기 어렵다는 점이었습니다.

쪽지·메신저·문서 중심의 요청은 빠르지만 최신 요구사항, 변경 이유, 담당자와 일정이 분리되기 쉬웠습니다. PO가 화면 수준까지 먼저 고정하고 UX가 후반에 다듬는 방식도 문제 정의와 해결안 탐색의 역할을 흐리게 만들었습니다.

01.1 / FRICTION

반복해서 시간을 빼앗는 지점을
협업의 마찰로 나눠봤습니다.

누가 일을 못해서가 아니라, 정보와 판단이 남는 위치가 서로 달랐기 때문에 같은 확인과 논쟁이 반복됐습니다.

01 / FRICTION

일을 느리게 만드는 구조

쪽지·메신저에 흩어진 요청 · 최신 버전 확인 · PPT 중심 화면 선결정 · 일정 싱크 불일치 · 개발의 늦은 참여 · 담당 범위 불명확 · 피드백 근거 휘발 · 비클라우드 문서

02 / RECORD

남겨야 했던 것

문제 정의 · 요구조건 · 대안과 근거 · 결정 이력 · Owner · 일정·상태 · 리뷰 맥락 · 다음 과제의 학습

01.2 / AS-IS

화면을 만드는 순서보다,
의사결정이 고정되는 순서를 먼저 봤습니다.

01 / REQUEST

여러 채널로 요청

요청과 수정사항이 쪽지·메신저·문서에 나뉘어 최신 맥락을 다시 확인해야 했습니다.

02 / FIX

화면이 먼저 고정

문제와 요구조건보다 버튼·플로우·URL이 먼저 정해져 대안 탐색의 폭이 줄었습니다.

03 / DESIGN

UX가 후반에 참여

구조를 바꾸기 어려운 단계에서 화면 완성도를 높이는 역할로 좁아질 수 있었습니다.

04 / REVIEW

결정이 흩어짐

누가 왜 바꿨는지, 어떤 판단이 최종인지 다음 프로젝트에서 재사용하기 어려웠습니다.

결론

협업 툴을 바꾸는 것보다 먼저, 문제·역할·결정이 남는 위치를 하나의 흐름으로 연결해야 했습니다.

02

문제·역할·결정을 분리하고,
다시 연결하는 기준을 만들었습니다.

PO는 문제와 정책·요구조건을 명확히 하고, UX는 사용자 흐름과 화면 대안을 구체화하며, 개발과 사업은 기술·일정·운영 제약을 앞에서 함께 검토하는 구조를 목표로 했습니다.

02.1 / PRINCIPLES

협업의 기준도 화면 설계처럼
단순한 질문으로 정리했습니다.

01 / WHY

화면보다 문제를 먼저 봅니다.

무엇을 만들지보다 왜 필요한지와 해결해야 할 사용자·사업 문제를 먼저 합의합니다.

02 / ROLE

역할의 경계를 분명히 합니다.

문제·정책, UX 설계, 기술 제약과 실행 책임이 어디에서 만나야 하는지 구분합니다.

03 / PROTOTYPE

말보다 동작으로 확인합니다.

정적 문서만으로 설명하기 어려운 흐름은 실제로 작동하는 프로토타입으로 빠르게 검토합니다.

04 / DECISION

피드백보다 결정을 남깁니다.

취향성 코멘트가 아니라 무엇을 왜 선택했는지 판단 근거와 결과를 기록합니다.

05 / OWNER

일정과 책임을 연결합니다.

요청 문서와 별도로 움직이던 일정·담당자·상태를 실제 실행 단위와 연결합니다.

06 / LEARN

같은 문제를 다시 풀지 않습니다.

완료된 과제의 판단 기준과 예외를 다음 프로젝트에서 재사용할 수 있게 남깁니다.

03

결국 협업 흐름을,
문제에서 학습까지 이어지게 설계했습니다.

도구 자체가 답은 아니었습니다. Figma, Teams, Planner와 AI 프로토타입은 각각 문제 정의·설계·리뷰·일정·검증을 연결하기 위한 수단으로 두고, 한 과제의 맥락이 다음 단계에서 끊기지 않게 만드는 데 집중했습니다.

03.1 / TO-BE FLOW

요청이 들어온 순간부터
판단이 남는 일곱 단계를 정의했습니다.

01 / PROBLEM

문제 정의

사용자·사업 관점에서 해결해야 할 문제를 먼저 맞춥니다.

02 / REQUIREMENT

요구조건

정책·목표·필수 조건과 제약을 문서화합니다.

03 / UX FLOW

대안 설계

UX가 사용자 흐름과 화면 구조를 여러 안으로 구체화합니다.

04 / PROTOTYPE

동작 검증

Figma와 AI 코딩으로 핵심 인터랙션을 빠르게 확인합니다.

05 / REVIEW

근거와 결정

유관부서 리뷰의 피드백과 최종 판단을 한 흐름에 남깁니다.

06 / OWNER

일정·담당

할 일의 Owner, 일정, 상태를 실제 과제와 연결합니다.

07 / LEARN

학습 축적

예외와 판단 기준을 다음 과제의 출발점으로 남깁니다.

03.2 / ROLE

누가 화면을 그리느냐보다,
어떤 판단을 책임지는지 다시 나눴습니다.

PO

문제·정책·요구조건

사업 목표와 정책, 시스템 조건을 명확히 하고 무엇을 해결해야 하는지 정의합니다.

PROBLEM · REQUIREMENT

UX DESIGN

사용자 흐름·화면 대안

정해진 화면을 다듬는 것이 아니라 문제에 맞는 구조와 인터랙션을 구체화하고 검증합니다.

FLOW · INTERACTION · PROTOTYPE

DEV

기술 제약·구현 가능성

후행 전달이 아니라 설계 단계에서 기술 조건과 예외를 함께 검토합니다.

FEASIBILITY · EXCEPTION

BUSINESS

우선순위·운영 조건

실제 운영과 매출, 정책 우선순위를 초기 판단에 연결합니다.

PRIORITY · OPERATION
