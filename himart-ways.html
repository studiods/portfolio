문제는 도구보다,
결정이 어디에 남는지 알기 어렵다는 점이었습니다.

요청·변경·책임이 흩어지는 협업을 다시 정의했습니다.

01.1 / FRICTION

반복해서 시간을 빼앗는 지점을
협업의 마찰로 나눠봤습니다.

정보와 판단이 흩어져 논쟁이 반복됐습니다.

I. / STRUCTURE

일을 느리게 만드는 구조

요청·버전·일정·책임·피드백이 여러 곳에 흩어졌습니다.

II. / RECORD

남겨야 했던 것

문제·요구조건·근거·결정·Owner·일정·학습을 남겼습니다.

01.2 / AS-IS

화면을 만드는 순서보다,
의사결정이 고정되는 순서를 먼저 봤습니다.

기존 협업은 네 단계로 흘렀지만 판단 근거가 다음 단계에 충분히 남지 않았습니다.

REQUEST 01
FIX 02
DESIGN 03
REVIEW 04
01 / REQUEST

여러 채널로 요청

요청과 수정사항이 여러 문서로 나뉘었습니다.

02 / FIX

화면이 먼저 고정

버튼·플로우·URL이 문제보다 먼저 고정됐습니다.

03 / DESIGN

UX가 후반에 참여

UX가 구조보다 화면 완성에 머물 수 있었습니다.

04 / REVIEW

결정이 흩어짐

변경 이유와 최종 판단을 재사용하기 어려웠습니다.

결론

문제·역할·결정이 하나의 흐름에 남아야 했습니다.

02

문제·역할·결정을 분리하고,
다시 연결하는 기준을 만들었습니다.

PO·UX·개발·사업의 판단 기준을 다시 연결했습니다.

02.1 / PRINCIPLES

협업의 기준도 화면 설계처럼
단순한 질문으로 정리했습니다.

여섯 가지 원칙을 모든 리뷰의 공통 기준으로 사용했습니다.

III.

화면보다 문제를 먼저 봅니다.

필요한 이유와 해결할 문제를 먼저 합의합니다.

IV.

역할의 경계를 분명히 합니다.

문제·UX·기술·실행 책임을 구분합니다.

V.

말보다 동작으로 확인합니다.

복잡한 흐름은 프로토타입으로 검토합니다.

VI.

피드백보다 결정을 남깁니다.

선택 이유와 결과를 기록합니다.

VII.

일정과 책임을 연결합니다.

일정·담당자·상태를 실행 단위에 연결합니다.

VIII.

같은 문제를 다시 풀지 않습니다.

판단 기준과 예외를 다음 과제에 남깁니다.
