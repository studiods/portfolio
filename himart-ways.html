문제는 오래된 방식 그 자체가 아니라, 불편함을 문제로 인식하지 못하고 계속 유지하는 데 있었습니다.

01.1

생각보다,
문제는 심각했습니다.

20년 전에 사용하던 방식을 아직도 유지하고 있었습니다.

01 / MEMO7 DAYS

일주일 뒤 사라지는 쪽지

작성 중 끊기면 내용이 날아가기도 했고, 요청·수정·승인 이력이 일주일 뒤 함께 사라졌습니다.

02 / WBSSTATIC

계획은 있지만 상태는 보이지 않았습니다.

WBS는 있었지만 누가 무엇을 얼마나 진행했는지 실시간으로 추적하기 어려웠습니다.

03 / STORYBOARDPPT

PO의 SB도 폐쇄형 파일로 흘렀습니다.

Storyboard를 PowerPoint로 작성하고 수정본과 배포도 쪽지로 전달해 최신 버전과 변경 이유가 흩어졌습니다.

04 / ROOMPAPER

회의실 일정도 종이로 조율했습니다.

회의실 밖에 종이를 붙여 예약했고, 일정 변경과 중복 확인도 사람이 직접 맞춰야 했습니다.

01.2

먼저 팀별로 어떻게 소통하고 일하는지 들어봤습니다.

툴을 정해 놓고 설득하지 않고, 팀별 인터뷰와 업무 관찰을 통해 필요한 구조부터 찾았습니다.

“진행 상황이 안 보이니 결국 담당자에게 다시 물어봐야 합니다.”VISIBILITY
“수정본과 자료가 여러 곳에 흩어져 다시 찾고 다시 보내는 일이 많습니다.”CONTEXT
“각자 소통하다 보니 같은 프로젝트에서도 서로 다른 우선순위로 움직입니다.”ALIGNMENT
“불편한 건 알지만 다른 부서도 쪽지를 쓰고 있어서 우리만 바꾸기 어렵습니다.”ADOPTION
“결정이 쪽지와 파일에 흩어져 나중에 왜 바뀌었는지 찾기 어렵습니다.”TRACEABILITY
“담당자가 자리를 비우면 어디까지 진행됐는지 다른 사람이 알기 어렵습니다.”HANDOFF

툴을 고르기 전에,
누가 무엇을 결정하는지부터 다시 나눴습니다.

PO·UX·개발·사업이 화면을 넘겨받는 관계가 아니라 문제를 함께 해결하는 구조를 목표로 했습니다.

02.1

누가 화면을 그리느냐보다,
어떤 판단을 책임지는지를 먼저 정의했습니다.

세부 설계 전에 PRD 기반 Sync와 Kick-off를 두고 목표·Scope·제약을 함께 검증하도록 했습니다.

01 / PO

문제·목표·정책과 우선순위

비즈니스 목표, 해결할 문제, 정책, PRD, 로드맵과 전체 일정·우선순위를 책임집니다.

02 / UX

사용자 흐름과 경험의 구체화

UX 방향, 정보 구조, Wireframe, Prototype, UI Design과 상세 경험의 완성도를 책임집니다.

03 / DEV

기술 가능성과 더 나은 대안

후반 구현자가 아니라 초반부터 참여해 기술 제약과 최신 스펙 적용 시 가능한 대안을 함께 결정합니다.

04 / BUSINESS

운영 조건과 사업 우선순위

현장·운영·매출·정책 조건을 공유하고 목표와 실제 운영 사이의 간극을 함께 조정합니다.

02.2

업무의 흐름도 전달 중심에서,
공동 판단이 남는 흐름으로 바꿨습니다.

문제와 Scope를 먼저 공동으로 정의

문제·목표 정의

02.3

결국 기준은 단순했습니다.
말이 아니라 일이 남아야 했습니다.

01

비공식 요청을 공식 업무로 바꿉니다.

1:1 쪽지와 구두 요청을 줄이고 프로젝트 채널·Ticket에 기록합니다.

02

목표와 Scope를 설계 전에 맞춥니다.

PRD·Kick-off를 통해 무엇을 왜 하는지 먼저 합의합니다.

03

진행 상황을 묻지 않아도 보이게 합니다.

Owner·Due date·Status를 Planner에서 공유합니다.

04

자료와 논의를 한 공간에 둡니다.

파일·이슈·결정·댓글을 같은 프로젝트 맥락에 연결합니다.

05

회의는 안건이 있을 때 시작합니다.

Agenda와 필요한 문서를 사전에 공유하고 회의 후 결정을 남깁니다.

06

도구는 최소화하고 연결합니다.

Teams·Planner·Lists·Calendar를 중심으로 채널 수를 줄이고 다음 단계에서 Jira·자동화를 연결합니다.

03

각 팀의 의견을 모아,
우리 조직에 맞는 방식으로 실제 운영을 바꿨습니다.

03.1

무작정 도입하지 않고,
인터뷰부터 Pilot까지 순서대로 진행했습니다.

AIMMO 디자인 시스템 때와 마찬가지로 먼저 사용자와 환경을 파악하고 실행 가능한 기준을 만들었습니다.

01 / LISTEN

팀별 인터뷰

각 팀을 직접 찾아가 현재 방식과 불편, 필요한 기능을 수집했습니다.

02 / MAP

문제 구조화

휘발·중복·비가시성·R&R 충돌·일정 조율 문제로 묶었습니다.

03 / WORKSHOP

리더 논의

팀장·매니저들과 우리 조직에 필요한 프로세스와 도구를 함께 결정했습니다.

04 / PILOT

소규모 적용

Teams·Planner·Lists·Calendar를 실제 과제에서 먼저 사용했습니다.

05 / GUIDE

가이드 제작

업무 소통·프로젝트 관리·말머리·회의·일정 규칙을 문서화했습니다.

06 / ROLLOUT

부서별 배포

1차 가이드를 배포하고 부서별 사용을 시작해 정착 단계로 이동했습니다.

03.2

쪽지를 없애는 것이 목표가 아니라,
업무가 남고 연결되는 환경을 만들었습니다.

TEAMS / CHANNEL

공식 소통 공간을 만들었습니다.

타 부서 요청은 Webex·Teams로 유도하고, 공식 논의는 Channel·Thread에서 이어지도록 전환했습니다.

PLANNER / TICKET

프로젝트 상태가 보이게 했습니다.

업무를 Ticket 단위로 등록하고 Owner·일정·상태·자료·문제점을 한 공간에서 공유했습니다.

LISTS / REQUEST

반복 요청은 구조화했습니다.

정형 요청과 데이터 취합 등 반복 업무는 Lists 기반으로 형식을 맞춰 누락과 재확인을 줄였습니다.

CALENDAR / SCHEDULE

일정을 투명하게 공유했습니다.

공용 일정과 휴가·외근·집중 업무를 Calendar에 연결해 일정 확인과 조율을 한 곳에서 진행하도록 했습니다.

ROOM / RESERVATION

종이 예약을 온라인으로 바꿨습니다.

회의실 예약 프로세스와 페이지를 제작해 배포했고, 종이를 붙여 조율하던 방식을 온라인 예약으로 전환했습니다.

NEXT / AUTOMATION

다음은 채널 축소와 자동화입니다.

Jira 도입, 채널 통합, Power Automate 연계를 통해 상태 확인과 반복 알림을 더 줄이는 방향으로 확장하고 있습니다.

03.3

툴만 배포하면 다시 예전 방식으로 돌아갑니다.
그래서 사용하는 규칙까지 함께 만들었습니다.

01

[공지] [요청] [공유] [승인] 말머리를 사용합니다.

메시지 목적을 열기 전에 파악하고 필요한 사람이 빠르게 반응할 수 있게 했습니다.

02

공식 업무는 개인 쪽지가 아닌 Channel에 남깁니다.

개인 대화에 프로젝트 맥락이 갇히지 않도록 했습니다.

03

회의 전에 Agenda와 필요한 자료를 공유합니다.

준비되지 않은 회의를 줄이고 결정해야 할 내용을 명확히 했습니다.

04

변경은 원본 Ticket에서 이어서 논의합니다.

수정본을 새로 전달하는 대신 이유와 영향도를 기존 업무 이력에 연결합니다.

05

진행률보다 상태와 Blocker를 공유합니다.

누가 바쁜지보다 무엇이 막혀 있는지 보이게 해 문제 해결 속도를 높입니다.

06

업무 종료 후에도 결정과 자료가 남아야 합니다.

다음 프로젝트에서 같은 질문을 다시 하지 않도록 결과와 학습을 자산화합니다.

04

정착 초기라 실측 성과는 없습니다.
그래서 예상 효과와 초기 피드백을 분리했습니다.

숫자는 현재 프로세스를 기준으로 계산한 시뮬레이션이며, 실제 성과처럼 표현하지 않았습니다.

04.1

기존 방식과 개선 방식을 같은 조건으로 놓고,
소통·검색·조율에 쓰는 시간을 보수적으로 계산했습니다.

04.3

아직 숫자로 증명할 단계는 아니지만,
초기 사용자의 반응은 같은 방향을 가리키고 있습니다.

현재는 구두 피드백과 사용 정착을 확인하는 단계이며 정량 KPI는 다음 단계에서 측정합니다.

“관리되고 있으니 진행 상황을 매번 물어보지 않아도 돼서 좋습니다.”STATUS VISIBILITY
“자료가 한 공간에 같이 있으니 찾고 다시 보내는 소통이 확실히 줄었습니다.”SHARED CONTEXT
“목표와 방향을 같이 보고 시작하니 결과물도 이전보다 더 잘 맞는 것 같습니다.”ALIGNMENT
“프로젝트 히스토리가 남으니 누가 무엇을 왜 바꿨는지 다시 확인하기 쉬워졌습니다.”TRACEABILITY
04.4

다음 단계에서는 좋아졌다는 느낌이 아니라,
실제 운영 데이터로 검증하려고 합니다.

01 / TIME

상태 확인·자료 탐색 시간

업무 현황을 묻고 최신 자료를 찾는 데 걸리는 시간을 Before/After로 측정합니다.

02 / REWORK

변경·재작업 횟수

목표·Scope·정책의 불일치로 발생하는 재작업과 수정 왕복 횟수를 추적합니다.

03 / LEAD TIME

요청부터 완료까지의 Lead Time

Ticket 생성부터 완료까지 걸리는 시간과 Blocker 체류 시간을 측정합니다.

04 / TRACE

결정 기록률

중요 변경이 이유·Owner·결정과 함께 남는 비율을 확인합니다.

05 / ADOPTION

공식 Channel·Ticket 정착률

쪽지·개별 요청이 아닌 공식 업무 공간에서 처리되는 비율을 추적합니다.

06 / SCALE

Jira·Automation으로 확장

프로세스가 안정되면 Jira와 Power Automate를 연결해 반복 운영까지 줄입니다.

LEADERSHIP

제가 바꾸려 했던 것은 메신저가 아니었습니다. 문제를 함께 정의하고, 진행 상황을 서로 묻지 않아도 보이며, 결정과 학습이 다음 업무까지 남는 조직의 운영 방식을 만드는 일이었습니다.
