01

화면을 만들기 전에,
왜 제품들이 서로 다르게 느껴지는지부터 확인했습니다.

입사 직후 팀원 면담과 설문으로 팀이 멈춰 있던 이유를 먼저 수집했습니다.

01.1 / TEAM VOICE

가장 먼저 나온 문제는,
디자인 시스템이 없다는 것이었습니다.

공통 에셋뿐 아니라 제대로 합의된 디자인 규칙도 없어 비슷한 기능조차 서비스마다 다른 UI와 UX로 제공되고 있었습니다.

“비슷한 기능인데 서비스마다 UX가 달라 불편하다는 이야기가 많아요.”PRODUCT CONSISTENCY
“디자인 시스템을 만든 경험이 없어 어떻게 시작해야 하는지 모르겠어요.”STARTING POINT
“시간이 없어 공통 디자인 에셋도 못 만들었어요.”RESOURCE
“UX를 조금만 바꿔도 불편함을 호소하셔서 손을 못 대요.”LIVE SERVICE
“한 번에 전체 적용을 못하면 계속 화면이 달라져서 이상할 것 같아요.”ADOPTION
SOURCE - 기존 포트폴리오 AIMMO DESIGN SYSTEM / 입사 후 1:1 미팅을 통해 수집한 디자인 시스템 관련 요구사항
01.2 / WHY IT STOPPED

문제는 컴포넌트가 아니라,
공감대와 시작 방법이 모두 없다는 데 있었습니다.

라이브 서비스, 협업 부서, 제작 경험, UX 방향성의 문제가 서로 얽혀 있어 전체 교체 방식으로는 시작하기 어려웠습니다.

01

공감대 부족

협업 부서와 디자인 시스템 제작 필요성이 충분히 공유되지 않았습니다.

02

라이브 서비스

실시간 운영 중이라 전체 화면을 한 번에 교체할 수 없었습니다.

03

제작 경험 부족

팀 안에 구축 경험이 없어 어디서부터 정의할지 어려웠습니다.

04

경험의 단절

서비스마다 다른 UI와 UX가 하나의 제품군이라는 인식을 약하게 만들었습니다.

01.3 / REFRAME

그래서 완성된 시스템을 목표로 시작하지 않았습니다.
지금 꼭 필요하고 자주 쓰는 것부터 만들었습니다.

현재 리소스를 먼저 전수 조사하고, 실제 제품에서 반복 사용되는 필수 컴포넌트부터 정의해 적용 범위를 넓히는 방식으로 시작했습니다.

CORE
FIRST

전체를 한 번에 바꾸는 계획보다,
오늘의 제품 개발에서 바로 사용할 수 있는 공통 기준을 먼저 만들었습니다.

02

큰 계획보다,
팀이 동시에 움직일 수 있는 제작 방식을 먼저 만들었습니다.

판단 기준을 정하고 담당자를 세워 시스템과 팀을 함께 만들었습니다.

02.1 / PRINCIPLES

명확성, 동일 경험, 사전 검증.
여섯 가지 원칙으로 판단 기준을 맞췄습니다.

제작 전에 무엇을 지켜야 하는지부터 합의해 중복 제작과 뒤늦은 논쟁을 줄였습니다.

01 / CLARITY

명확성을 가장 중요한 기준으로 정의했습니다.

02 / REAL CONTEXT

실사용자의 근무 환경과 사용 패턴을 먼저 검증했습니다.

03 / STANDARDIZE

서비스별 사이즈와 색상 등 공통 규격을 통일했습니다.

04 / SAME UX

동일한 기능의 UX는 같은 컴포넌트를 사용했습니다.

05 / CONSENSUS

신규 UI 컴포넌트는 전체 동의를 거쳐 추가했습니다.

06 / TOKEN

시스템을 토큰화해 개발팀의 적용 효율을 높였습니다.

02.2 / PARALLEL OWNERSHIP

파트를 나눠 맡기자,
속도와 오너십이 함께 생겼습니다.

색상·폰트·그리드·그래픽 스타일·아이콘을 디자이너별로 분배해 병렬로 제작하고 파트별 담당자를 명확히 했습니다.

01COLOR

색상 체계와 상태 표현 기준

02TYPE

폰트 위계와 텍스트 규칙

03GRID

레이아웃과 화면 구조 기준

04GRAPHIC

그래픽 스타일과 표현 원칙

05ICON

아이콘 규격과 사용 기준

업무를 병렬로 나누자 제작 속도가 빨라졌고,
담당 영역이 생기면서 디테일을 스스로 높이는 좋은 시너지가 만들어졌습니다.

02.3 / GUIDED BUILD

경험이 없던 팀에는,
제가 먼저 겪었던 시행착오를 프로세스로 전달했습니다.

세 번 이상 디자인 시스템을 구축했던 경험을 바탕으로 우선순위, 검증 방법, 협업 방식과 제작 노하우를 공유했습니다.

03

완성 및 고도화

피드백 반영 · 개발 논의 · 라이브러리와 토큰 확장

03

문서로 정의한 기준을,
실제 제품과 개발 흐름 안에서 계속 검증했습니다.

만드는 것과 적용하는 것을 분리하지 않고 서비스에 넣으며 고도화했습니다.

03.1 / BUILD LOOP

한 번에 완성하지 않고,
검증하고 적용하며 단계적으로 키웠습니다.

초기 정의 단계에서 내부 검증을 반복해 중복 리소스와 추후 협의를 줄이고, 서비스 간 교차 적용으로 범용성을 확인했습니다.

01

수집

현재 서비스의 리소스와 반복 패턴을 모두 모았습니다.

02

2~3차 검증

내부 협의와 비교 적용으로 중복과 예외를 줄였습니다.

03

서비스 적용

라이브 제품에 넣어 실제 사용 가능성을 확인했습니다.

04

고도화

피드백을 다시 시스템과 다음 컴포넌트에 반영했습니다.

03.2 / DEVELOPMENT

개발팀과 계속 확인하며,
라이브러리와 토큰을 병렬로 만들었습니다.

지속적인 미팅과 인터뷰로 부족한 부분을 빠르게 찾고 버전을 업데이트해 실제 개발 과정의 효율을 높였습니다.

INTERVIEW

부족한 부분을 개발팀과 바로 확인했습니다.

디자인 산출물만 전달하지 않고 적용 과정에서 필요한 규칙과 예외를 계속 수집했습니다.

VERSIONING

사용하면서 시스템 버전을 계속 올렸습니다.

실제 서비스에서 발견한 문제를 다음 버전에 반영해 문서와 제품의 간극을 줄였습니다.

LIBRARY / TOKEN

개발에 필요한 형태까지 함께 만들었습니다.

라이브러리화와 토큰화를 병렬로 진행해 디자인 시스템이 실제 제품 개발 속도로 이어지게 했습니다.

03.3 / REAL WORK ENVIRONMENT

규칙을 맞추는 데서 끝내지 않고,
실사용자의 작업 환경까지 기준에 넣었습니다.

정확성과 신속성이 중요한 크라우드 워커의 환경을 확인해 빠른 탐색과 실행이 가능한 UI로 정리했습니다.

실제 작업 조건이
컴포넌트의 기준이 되었습니다.

저조도 환경을 고려한 다크 테마노트북 해상도에 최적화된 정보 구조빠르게 탐색하고 실행할 수 있는 명확한 위계서비스 간 동일 기능의 공통 컴포넌트 적용
04

공통 기준이 쌓이자,
팀의 시간과 제품의 품질이 함께 달라졌습니다.

성과는 컴포넌트 수보다 업무 속도·소통·오너십 변화에서 더 선명하게 나타났습니다.

04.1 / IMPACT

제작과 소통 시간은 줄고,
UX를 고민하는 시간은 늘었습니다.

디자인 시스템 적용 전후의 업무 흐름을 인터뷰와 협업 기록으로 비교했습니다.

−72%

GUI 디자인 제작 소요 시간

반복 컴포넌트 제작과 확인 과정이 줄어 디자인 업무 시간이 크게 감소했습니다.

−63%

협업 부서와의 소통 시간

같은 기준을 보며 논의할 수 있어 화면과 규칙을 설명하는 비용이 줄었습니다.

−38%

Front-end 전체 개발 소요 시간

전체 리소스의 약 1/3만 적용된 시점에도 개발 효율 개선이 확인됐습니다.

+45%

UX 설계·기획 고려 시간

PO도 디자인 시스템으로 와이어프레임을 만들며 화면을 보면서 문제와 개선점을 더 많이 논의할 수 있었습니다.

SOURCE - 기존 포트폴리오 AIMMO DESIGN SYSTEM / 디자이너·개발자·PO 인터뷰 및 Asana 협업 기록을 통해 확인한 생산성 증감 수치
04.2 / TEAM IMPACT

쉽지 않은 과정이었지만,
팀이 직접 변화를 체감하는 경험으로 남았습니다.

업무와 시스템 구축을 병행하느라 시간이 많이 들고 소통도 어려웠지만, 공통 자산이 쌓이면서 변화가 눈에 보이기 시작했습니다.

SPEED

반복해서 만들던 시간이 실제 제품 개선 시간으로 바뀌었습니다.

같은 요소를 다시 확인하고 제작하는 과정이 줄어들면서 팀 전체의 업무 속도가 올라갔습니다.

OWNERSHIP

담당 파트가 생기자 디테일을 스스로 끌어올렸습니다.

파트별 오너십이 생기면서 담당 디자이너가 기준과 완성도를 더 깊게 고민하는 문화가 만들어졌습니다.

PRIDE

함께 만든 시스템이 실제 일을 바꾸는 경험이 보람으로 남았습니다.

제작에 참여한 팀원들도 생산성 향상을 직접 경험하면서 결과에 대한 만족과 자부심을 느꼈습니다.

WHAT THE SYSTEM CHANGED

디자인 시스템은 UI를 맞춘 프로젝트가 아니라,
팀이 같은 기준으로 더 빠르게 좋은 제품을 만드는 방식이 되었습니다.
