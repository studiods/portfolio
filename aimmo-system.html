완성된 가이드보다, 팀이 바로 쓰고 함께 키울 수 있는 기준부터 만들었습니다.

01

입사 직후,
팀이 왜 같은 제품을 다르게 만들고 있는지부터 확인했습니다.

팀빌딩을 위한 1:1 면담과 설문에서 가장 먼저 반복된 문제는 디자인 시스템의 부재였습니다.

01.1 / TEAM VOICE

디자인 시스템뿐 아니라,
함께 지키는 디자인 규칙 자체가 없었습니다.

비슷한 기능도 제품마다 UI와 UX가 달라 하나의 프로세스로 이어지는 제품군이라고 보기 어려운 상태였습니다.

“비슷한 기능인데 서비스마다 UX가 달라 불편하다는 이야기가 많아요.”PRODUCT CONSISTENCY
“디자인 시스템을 만든 경험이 없어 어떻게 시작해야 하는지 모르겠어요.”STARTING POINT
“시간이 없어 공통 디자인 에셋도 못 만들었어요.”RESOURCE
“한 번에 전체 적용을 못하면 계속 화면이 달라져서 이상할 것 같아요.”ADOPTION
SOURCE - 기존 포트폴리오 AIMMO DESIGN SYSTEM / 입사 후 1:1 미팅 요구사항
01.2 / WHY IT STOPPED

문제는 의지가 아니라,
시작할 수 있는 조건과 방법이 없다는 데 있었습니다.

라이브 서비스, 협업 부서의 공감대, 구축 경험 부족, 제품별로 달라진 UX가 동시에 얽혀 있었습니다.

01

공감대 부족

협업 부서까지 필요성이 충분히 공유되지 않았습니다.

02

라이브 서비스

전체 UI를 한 번에 교체할 수 없는 상황이었습니다.

03

경험 부족

팀 안에 구축 경험이 없어 시작점 설정이 어려웠습니다.

04

제품 경험 단절

같은 제품군에서도 기능과 화면의 기준이 달랐습니다.

01.3 / REFRAME

그래서 디자인 시스템을 만드는 일이 아니라,
팀이 같은 기준으로 제품을 만드는 일로 다시 정의했습니다.

전체 교체를 목표로 잡지 않고 현재 업무에 바로 필요한 기준과 반복 사용되는 컴포넌트를 먼저 만들기로 했습니다.

FROM

각 제품마다 다시 판단하고 다시 만드는 방식

→TO

같은 기준을 공유하고 반복해서 재사용하는 방식

02

완성된 시스템보다,
지금 제품에 바로 필요한 기준부터 만들었습니다.

리소스를 전수 조사하고 가장 많이 쓰는 컴포넌트부터 우선순위를 정해 시작했습니다.

02.1 / CORE FIRST

한 번에 전부 만들지 않고,
필수·반복 컴포넌트부터 정의했습니다.

현재 리소스를 모두 수집한 뒤 사용 빈도와 필요도를 기준으로 우선순위를 정했습니다.

01RESOURCE AUDIT

서비스별 기존 UI와 에셋을 수집하고 중복·차이를 확인했습니다.

02FREQUENCY

지금 가장 자주 쓰는 컴포넌트를 먼저 선별했습니다.

03CORE FIRST

바로 적용 가능한 필수 컴포넌트부터 제작했습니다.

04EXPAND

검증된 기준을 이후 에셋과 서비스로 점진 확장했습니다.

02.2 / PRINCIPLES

만들기 전에,
무엇을 지킬지부터 합의했습니다.

사례를 그대로 복제하지 않고 에이모의 제품과 사용자 환경에 필요한 여섯 가지 원칙을 정했습니다.

01 / CLARITY

명확성을 가장 중요한 기준으로 정의했습니다.

02 / REAL CONTEXT

실사용자의 근무 환경과 사용 패턴을 사전 검증했습니다.

03 / STANDARDIZE

서비스별 사이즈와 색상 등 공통 규격을 통일했습니다.

04 / SAME UX

동일한 기능의 UX는 같은 컴포넌트를 사용했습니다.

05 / CONSENSUS

신규 UI 컴포넌트는 팀의 합의를 거쳐 추가했습니다.

06 / TOKEN

토큰화를 통해 개발팀의 적용 효율까지 고려했습니다.

02.3 / BUILD LOOP

정의하고 끝내지 않고,
검증하고 적용하며 계속 보완했습니다.

컴포넌트 정의 → 에셋 제작 → 시스템 고도화를 큰 흐름으로 두고, 내부 검증과 개발 협의를 반복했습니다.

03

제가 대신 만드는 것이 아니라,
팀이 함께 만들 수 있는 제작 방식을 설계했습니다.

파트를 나누고 오너를 세우고, 구축 경험을 팀의 노하우로 바꾸는 데 집중했습니다.

03.1 / PARALLEL OWNERSHIP

색상·폰트·그리드·그래픽·아이콘을 나눠 맡기자,
속도와 오너십이 함께 생겼습니다.

각 디자이너가 하나의 파트를 책임지고 병렬로 진행해 전체 제작 속도를 높였습니다.

01COLOR

색상 체계와 상태 표현

02TYPE

폰트 위계와 텍스트 규칙

03GRID

레이아웃과 화면 구조

04GRAPHIC

그래픽 스타일과 표현 원칙

05ICON

아이콘 규격과 사용 기준

PARALLEL
OWNERSHIP

담당 영역이 명확해지자 스스로 기준을 더 깊게 고민했고,
파트별 디테일도 빠르게 높아졌습니다.

03.2 / GUIDED BUILD

팀에는 처음이었지만,
저에게는 세 번 이상 경험해 본 구축 과정이었습니다.

이전 디자인 시스템 구축 경험을 바탕으로 제작 순서, 검증 방식, 컴포넌트 정의 노하우를 가이드해 시행착오를 줄였습니다.

01

PROCESS

무엇부터 정의할지 제작 순서를 설계했습니다.

02

REVIEW

2~3차 내부 검증으로 중복과 재논의를 줄였습니다.

03

KNOW-HOW

컴포넌트화와 운영 노하우를 팀에 전달했습니다.

04

OWNERSHIP

결정권을 나눠 팀이 스스로 시스템을 키우게 했습니다.

03.3 / DEVELOPMENT

디자인 파일에서 끝내지 않고,
개발팀이 실제로 쓰는 시스템으로 연결했습니다.

개발팀과 지속적으로 미팅하고 부족한 부분을 빠르게 보완하며 라이브러리화와 토큰화를 병렬로 진행했습니다.

01 / INTERVIEW

개발 과정의 막히는 지점을 계속 확인했습니다.

디자인 정의와 실제 구현 사이의 차이를 빠르게 수집했습니다.

02 / LIBRARY

재사용 가능한 구조로 라이브러리화를 진행했습니다.

같은 기능을 다시 만드는 비용을 줄이는 방향으로 정리했습니다.

03 / TOKEN

토큰화를 병렬로 진행해 적용 속도를 높였습니다.

디자인과 개발이 같은 값을 바라볼 수 있도록 연결했습니다.

04

디자인 시스템은 화면을 통일하는 데서 끝나지 않고,
팀의 일하는 방식을 바꿨습니다.

제작·개발·소통 비용이 줄었고, 함께 만든 팀원들에게는 결과물에 대한 오너십이 남았습니다.

04.1 / PRODUCTIVITY

일부 리소스만 적용된 단계에서도,
업무 방식의 변화는 숫자로 나타났습니다.

디자이너·개발자·PO 인터뷰와 Asana에서 확인한 제작 전후 생산성 변화입니다.

-72%

GUI 디자인 제작 시간

컴포넌트 확인과 반복 제작에 필요한 시간이 크게 줄었습니다.

-63%

협업 부서와의 소통 시간

같은 화면 기준을 보며 설명하고 확인하는 비용이 감소했습니다.

-38%

Front-end 개발 소요시간

당시 전체 리소스의 약 1/3 적용 단계에서도 개발 효율이 높아졌습니다.

+45%

UX 설계·기획 고려시간

단순 UI 확인보다 사용자 경험과 문제 해결에 더 많은 시간을 쓸 수 있었습니다.

SOURCE - 포트폴리오 18p / 디자이너·개발자·PO 인터뷰 및 Asana 생산성 변화 수치
04.2 / TEAM IMPACT

시간은 많이 들었지만,
팀이 함께 만든 만큼 결과는 팀의 자산으로 남았습니다.

업무와 병행해 쉽지 않았고 소통에도 많은 시간이 필요했지만, 실제 생산성 향상을 경험하면서 참여한 팀원들도 결과에 큰 보람과 자부심을 느꼈습니다.

01 / SPEED

반복 제작보다 문제 해결에 시간을 쓰게 됐습니다.

02 / OWNERSHIP

파트별 담당자가 생기며 디테일과 책임감이 함께 높아졌습니다.

03 / SHARED LANGUAGE

디자인·개발·PO가 같은 화면과 기준으로 대화하게 됐습니다.

04.3 / WHAT REMAINED

결국 남은 것은 컴포넌트 묶음이 아니라,
팀이 함께 판단하고 제품을 만드는 공통 언어였습니다.

DESIGN SYSTEM → TEAM SYSTEM

제가 가진 구축 경험을 기준으로 시작했지만,
마지막에는 팀이 스스로 만들고 개선할 수 있는 시스템으로 남겼습니다.
